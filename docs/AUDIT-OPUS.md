# AUDIT-OPUS - DQ10 (athena_p1) mainline U-Boot + Armbian eMMC reflash

Auditor: Opus agent, 2026-10-29. Independent review of the Sonnet build package (the working copy of this repository, host paths removed).
Method: read every script/config, re-derived the key facts from sources (U-Boot v2026.10, TF-A v2.15.0 and Linux v6.18.53 trees in WSL kali, vendor `live-fdt`, vendor boot0), inspected the rootfs read-only with `debugfs` (no mount), and ran **read-only** ADB commands on the stick (`lpdump`, `dmctl list/table`, `snapshotctl dump`, `getprop`, `cat /sys/...`, `dd if=... | sha256sum`). Nothing was written to the stick (checked afterwards that `snapshotctl dump` created no state file in `/metadata/ota`). No package file was changed.

## Verdict: **GO-WITH-FIXES**

No BLOCKER was found: the image, MBR, SPL, FIT, boot script, fstab, partition math, staging region, commit order and wipe ranges are internally consistent and match the device. The DRAM parameters were decoded correctly and match mainline's hard-coded LPDDR3 mode registers exactly. The two residual risks that can still brick the stick (an untested DRAM setup, and no proven recovery path) are inherent to the approach. The owner accepted them, and they cannot be fixed by editing files. Before running the plan, fix the HIGH items: H2 (the "safety net" SD-card path is broken by the U-Boot DT) and H3 (the plan's procedure text). Also take the cheap MEDIUM mitigations (M1 stop `update_engine`, M4 SSH exposure).

## Findings, ranked

### BLOCKER
None.

### HIGH

**H1. Two risks remain that no file change can remove: untested DRAM init and no recovery (accepted risk, stated here for the record).**
- Mainline U-Boot has exactly one H616-LPDDR3 board, `tanix_tx1_defconfig`, and it runs at the Kconfig default **720 MHz** (`arch/arm/mach-sunxi/Kconfig`: `default 720 if MACH_SUN50I_H616`; `tanix_tx1_defconfig` has no `DRAM_CLK`). At 600 MHz the driver takes the `if (para->clk <= 672) writel(0xf, PHY0+0x20)` branch (`dram_sun50i_h616.c:1009`). No LPDDR3 board in mainline has run that branch.
- TPR13 = 0x6061 has bits 0, 5, 6, 13 and 14 set. The mainline H616 driver has no TPR13 field at all (the fields it uses are clk, type, dx_odt, dx_dri, ca_dri, odt_en, tpr0, tpr2, tpr6, tpr10, tpr11, tpr12), so dropping TPR13 matches every mainline H616 board. Its BSP meaning (bit 0 = "auto-scan result valid, use para1/para2"; the others are unknown) could not be confirmed from any source. TPR1 is not used by the H616 driver either.
- **Evidence that lowers the risk** (verified by me): mainline's LPDDR3 path hard-codes MR1=0x83, MR2=0x1c, MR3=0x01 (`h616_lpddr3.c`: `init[3]=0x83001c`, MR3 `0x1`). That is **exactly** the vendor's `mr1/mr2/mr3` (0x83/0x1c/0x1) from boot0 and the DT. The vendor runs this same RL/WL set at 600 MHz.
- **If the SPL hangs, the stick is bricked until the case is opened** (see H2: even an SD card would not help in this case, because the same DRAM code runs from the card).
- **Fix:** none possible in files. Options to reduce it: (a) try the zero-write FEL probe (`reboot efex`, FLASH-PLAN 7.1-3) **before** the flash. If FEL works you can run the SPL's DRAM init over USB and you gain a recovery path. That changes the risk picture completely, so it is worth 10 minutes. (b) An alternative that keeps the vendor boot0 (proven DRAM init) and boots mainline U-Boot from the vendor `boot_package` was not built, and it would leave vendor code in place, which conflicts with the owner's requirement.

**H2. The SD-card test boot (Phase A) and SD recovery (7.1-1) cannot work with the shipped U-Boot. Its DT disables the SD controller.**
- Evidence: `uboot/u-boot.dtb` decompiled. `aliases { mmc0 = "/soc/mmc@4020000"; mmc1 = "/soc/mmc@4022000"; }`, and `mmc@4020000` has `status = "disabled"` (it is the TX1 DT, and the TX1 has no SD slot). The SPL can load the FIT from SD, because the SPL's MMC init does not depend on the DT. U-Boot proper, however, has **no SD device**: it never finds `boot.scr` on the card and falls back to scanning the eMMC.
  - Phase A, with Android still on the eMMC: U-Boot finds no boot script on the eMMC, tries USB/PXE and stops at the prompt with the LED solid. That looks exactly like the "DRAM hang" row in FLASH-PLAN 7, a misleading false negative.
  - 7.1-1 after the flash ("boot `dq10-armbian.img` from SD to fix the eMMC"): U-Boot from the card boots whatever is on the eMMC, not the card. Only `fel-sdboot.sunxi` would still be useful, and only if FEL works.
- **Fix:** rebuild U-Boot (main and recovery) with an SD node enabled, e.g. a local `sun50i-h313-dq10.dts` = TX1 + `&mmc0 { vmmc-supply = <&reg_dldo1>; bus-width = <4>; broken-cd; status = "okay"; };` (PI16 card-detect is unproven, so use `broken-cd`). Then regenerate `head-emmc-4MiB.bin`, `dq10-armbian.img` and all hashes, and re-diff against this audit. This also helps the eMMC install: a card inserted later becomes a real rescue medium for every failure that is not DRAM-related. Alternatively, if nothing is rebuilt, delete Phase A and 7.1-1 from the plan as "does not work with this U-Boot".

**H3. Plan text that could lead to a brick or to a false alarm.**
- FLASH-PLAN 6 (last paragraph) says: *"If adb is lost between steps 2 and 4, power-cycle: either FEL ... or our system."* FEL is unproven, so the "no valid image" state means a brick. The script runs detached and needs about 1 s. **Fix:** "If adb is lost, do NOT power-cycle. Reconnect (wait minutes if needed), read `/dev/dq10-commit.log`, and re-run the commit if it did not finish. Power-cycle only after `COMMIT-VERIFIED-OK`."
- FLASH-PLAN 8.2, last line: *"sha256 of sectors 0..8191 must still be d6e15f..."*. This is wrong after Armbian's resize. `armbian-resize-filesystem` runs `fdisk` (`d`/`n`/`w`), which rewrites the partition entry in sector 0, so the hash **will** change and look like tampering. **Fix:** compare sectors 1..8191 (`dd ... skip=1 count=8191`) against the same range of the head file, and check sector 0 with `sfdisk -d`.
- FLASH-PLAN 8.2 note: *"after resize p1 reaches the end of the disk (TAIL check is then vacuous)"*. Also wrong. The resize script keeps 1% spare and aligns to 16 MiB: lastsector = 30535680*99/100 aligned = **30212095**, so 323,584 sectors (158 MiB) stay unpartitioned. These were zeroed by the wipe, so the TAIL check is meaningful (good).

### MEDIUM

**M1. `update_engine` is running on a Virtual-A/B device, and a root-level backdoor is present. An OTA would allocate `_b` partitions in exactly the free part of `super` used for staging.**
- Evidence (stick): `ro.virtual_ab.enabled=true`, `ro.build.ab_update=true`, `init.svc.update_engine=running`, and `lpdump` "Header flags: virtual_ab_device". It also shows `system_b/vendor_b/product_b/vendor_dlkm_b` with empty extents, which are the slots an update fills from super free space. Current state is clean: `snapshotctl dump` reports "Update state: none", `/metadata/ota/snapshots` is empty, and there is no `scratch` partition.
- The egress block makes a download unlikely, but the root agent could apply a local payload. The plan re-checks `lpdump` and re-hashes before the commit, which catches this. It just costs a retry.
- **Fix:** before 5.1, `$ADB shell stop update_engine` (a user-approved runtime change, not persistent). Keep the 6.2 re-check of `lpdump` and 5.3. Optionally `stop` the root agent's service (`init.svc.rootaccess`, pid seen) for the duration.

**M2. Commit window with no valid boot image.**
- Between step 1 (sectors 17..8191 written) and step 3 (sector 16), neither the vendor boot0 (its checksum covers sectors 16..135, now overwritten, and the copy at sector 512 lies inside our FIT) nor our SPL is valid. The BROM then goes SD -> FEL, which is unproven, so this is a brick. The window is about 1 s and is entered only by power loss or a kernel crash. Every other interruption point is fine. I verified it: before step 1 lands, the vendor copy at 16 is still valid; after step 3 ours is valid (eGON checksum 0xf4086275 recomputed OK; FIT at sector 96; sector 512 holds FIT data, not an eGON header).
- **Fix:** ensure stable power (as planned), stop the malware service and `update_engine` first (M1), and run the commit only when `free` shows headroom (the stick showed **41 MB free RAM**, so the OOM killer could pick the commit shell). For example, `echo -1000 > /proc/self/oom_score_adj` at the top of `dq10-commit.sh`.

**M3. Wi-Fi modules built against vanilla 6.18.53 + Armbian config instead of Armbian's patched headers.**
- What I verified matches: vermagic `6.18.53-current-sunxi64 SMP preempt mod_unload aarch64`; `.gnu.linkonce.this_module` size **0x4c0, identical to the image's in-tree `cfg80211.ko`** (`struct module` layout matches); no `.BTF` section in our modules, so there is no BTF-mismatch load refusal (`CONFIG_DEBUG_INFO_BTF_MODULES=y` in-tree); `CONFIG_RANDSTRUCT_NONE=y` and `MODVERSIONS` off, so struct randomisation is not a concern; the compiler differs (GCC 16.1 vs 14.2).
- What I could not check: `cfg80211`/`net_device`/`sdio_func` layouts if Armbian patches touch those headers. A crash affects only Wi-Fi. Boot is not affected: the modules are loaded by udev, `panic_on_oops` is not set, and `systemd-udev-settle` (which the wipe waits for) times out rather than blocking forever.
- **Fix:** acceptable as is. Optionally compare against the image kernel's BTF (`/sys/kernel/btf/vmlinux` after boot, `pahole`), or rebuild on the device later with matching headers.

**M4. First boot exposes SSH with a known root password.**
- `ssh.service` is enabled, `sshd_config` has `PermitRootLogin yes`, root has Armbian's default password (`1234`, forced change at first login), and `/root/.not_logged_in_yet` is present. If Wi-Fi credentials are baked in (section 3), the stick sits on the network with root/1234 until someone logs in. Host keys are pre-baked in the image but are regenerated by `armbian-firstrun` (`rm -f /etc/ssh/ssh_host*; dpkg-reconfigure openssh-server`), so that part is fine.
- **Fix:** in `set-wifi.sh` also install an `authorized_keys` and drop a `sshd_config.d/10-dq10.conf` with `PasswordAuthentication no` (or set a root password hash), and log in promptly. The hotspot used was isolated, which limits exposure.

**M5. Wipe blocks boot for a long time, and its log may be hidden.**
- `dq10-wipe-vendor.service` (`Before=basic.target`, `TimeoutStartSec=3h`) writes about 13.4 GB with `conv=fsync` before `basic.target`. That is correct by design, but the HDMI console may show only the progress lines. If the wipe ever fails (`exit 1`), it re-runs and blocks **every** boot, and `armbian-resize-filesystem` never runs (`Requires=`). That failure is safe, but it should be documented.
- `/var/log` is moved to zram by `armbian-ramlog` (`ENABLED=true`). Lines written before or after that switch may land in different places, so `/var/log/dq10-wipe-vendor.log` can look truncated. `/var/lib/dq10/wipe-done` and the independent 8.2 checks are the real proof.
- **Fix:** document both points. Optionally log to `/var/lib/dq10/wipe.log` instead.

### LOW

- **L1.** `aic8800_bsp` has alias `sdio:c07v*d*` (any SDIO WLAN-class device). Harmless here.
- **L2.** `/lib/firmware` was pruned to `regulatory.db*` + AIC. The plan's fallback "USB Wi-Fi adapter" will usually need firmware that was removed (most USB Ethernet works without it).
- **L3.** `set-wifi.sh`: the PSK/SSID are placed in YAML double quotes unescaped, so a `"` or `\` breaks the file. Secrets passed as env vars end up in root's WSL shell history. FLASH-PLAN 2 says `sudo scripts/set-wifi.sh`, but `sudo` strips `SSID`/`PSK` (env_reset); that fails safely ("set SSID"). Use `sudo -E` or run as root, and prefix the command with a space or `unset HISTFILE`.
- **L4.** The SD image and the eMMC rootfs share filesystem UUID `e70cdb2c-...`. With both present, `root=UUID=` is ambiguous. On the SD image the wipe aborts (no boot partitions), so `Requires=` also blocks resize there, which is harmless.
- **L5.** FLASH-PLAN 7, the "LED solid then off" row: nothing in U-Boot turns PH6 off. The LED staying solid is the only U-Boot-stage signal.
- **L6.** FLASH-PLAN 6.3: read the log only after a few seconds; reading immediately can show an incomplete log.
- **L7.** Survivors of the wipe, by design: the eMMC **RPMB** area (`raw_rpmb_size_mult=0x20` = 4 MiB, keyed; cannot be read or erased without the vendor key; it is not executable), eMMC controller spare blocks, eFuses. The boot partitions are all zero (sha256 `bb9f8d...3af8` for both, re-read today). Everything else (vendor GPT incl. backup at the disk end, bootloader/env/misc/private/Reserve0/frp/boot/vendor_boot/super/userdata/media_data) lies in [8192, p1) or (p1_end, end] and is zeroed and verified.
- **L8.** `boot.cmd` probes `*0x10028` (an H3-era SRAM location; on H616 it is beyond the 64 KiB BROM). This is generic Armbian H616 behaviour that works on other H616 boards. It only prints a message.
- **L9.** The plan's `$ADB` is a convention and is never assigned. In Git Bash use `ADB="adb -s <stick-ip>:5555"`. Multi-word single-quoted remote commands are not path-mangled by MSYS (I confirmed with identical `dd if=/dev/... | sha256sum` invocations). Never run this from PowerShell 5.1, where `<` is unsupported (it would fail safely) and `|` would corrupt binary data.

## Claims verified as correct

1. **DRAM decode:** boot0 at disk byte 0x2000, words at +0x38 = `258 7 06060606 0d0d0d0d 0d0d 1 30eb 08001000 0 83 1c 1 0x10 ... 80000000 0 0 2fa88080 002f3359 aa889967 eeee8979 6061 0`. These are identical to `live-fdt` `dram_para[00..31]` (little-endian words vs big-endian DT cells give the same values, so the byte order is right). The index mapping matches `sunxi-fw` `register_mappings` (TPR13 = OFS(30)). The defconfig values are present in the built SPL as literals; the TX1 values are absent. ODT_EN is used only when TPR10 bit 30 is set (`dram_sun50i_h616.c:635..`), which is clear here, so the default 0x1 is correct. `CONFIG_SUNXI_DRAM_MAX_SIZE=4G`; size is auto-detected.
2. **PMIC:** vendor `pmu0` = `x-powers,axp1530` @0x36 on `twi@7081400` (R_TWI, PL0/PL1), the same bus U-Boot uses with `R_I2C_ENABLE`. U-Boot `axp_spl.c` AXP313 table: DCDC3 1200 mV gives reg 0x15 = 70, which is exactly 1.200 V; DCDC2 1000 mV; chip check `(id & 0xc8)==0x48`. TF-A v2.15 `sunxi_power.c` accepts 0x48/0x4b/0x4c and **sets no regulators** for AXP313 ("no regulators to set up"). DCDC1 is not settable in U-Boot for AXP313 (Kconfig `depends on` excludes it). The Linux DT pins dcdc3 at 1.2 V and keeps dcdc2 at 0.81-1.12 V. No dangerous voltage is set anywhere.
3. **SoC / CPU bin:** SID 0x33802100 (H618-family by prefix; plausible, M). Stick's `scaling_available_frequencies` = 480/720/1032/1104/1200/1296/1416/1512 MHz. 1032 and 1296 exist only in vendor bin **a0** (`opp-supported-hw = <0x01>`), so the vendor treats this chip as bin 0. Mainline maps unknown 0x2100 to bin 0 (`sun50i_h616_efuse_xlate` default case). Mainline bin-0 OPPs: 1416 MHz @1.10 V (vendor a0: 1.10 V), max 1416 (vendor a0 1512 @1.15 V not offered). This is safe and matches. SPL at 1008 MHz @1.0 V is above vendor a0's 1032 MHz @0.90 V point, so it is safe.
4. **BROM / SPL boot path:** the vendor boot0 is **eGON** (not TOC0) at sectors 16 and 512, which proves the BROM accepts eGON from the eMMC user area with the current EXT_CSD. The plan does not change EXT_CSD, and the boot partitions are zero, so the BROM path is unchanged up to reading sector 16. Mainline SPL (`board.c` `sunxi_valid_emmc_boot`) only uses a boot partition if BOOT_ACK + boot-bus + a valid eGON in it are present, so with zero boot partitions it reads the user area: safe even with `SUPPORT_EMMC_BOOT=y`. U-Boot FIT sector = max(0x40, 40960/512) + DATA_PART_OFFSET 0x10 = **96**, and the FIT magic `d00dfeed` is at sector 96 of the head image. The H616 high-location offset (+256 KiB) is confirmed in `board_spl_mmc_get_uboot_raw_sector`. EXT_CSD itself could not be read (see below), but it does not matter, for the reason above.
5. **Staging region:** `lpdump` today: super = `mmcblk0p9`, start 599040, 6291456 sectors (3 GiB), data from super-sector 2048, last extent ends 3422520 (disk 4021560); metadata is at the start (Virtual A/B layout). `dmctl` shows only 4 linear maps on 179:9, all mounted `ro`; no overlay/scratch; no snapshot state. Staging at disk 4194304..6815743 is inside the free tail (ends 74,752 sectors before super's end) and **is exactly the final p1** (MBR p1 start 4194304, size 2621440; no move). Preflight 4.2 hash re-read today = the backup's pre-boot hash (unchanged; value not published).
6. **Hashes:** `zcat rootfs.ext4.gz` gives 1,342,177,280 B, sha `2321d7a2...66f9`, identical to p1 inside `dq10-armbian.img`. `rootfs.ext4.gz` = `ba52307a...6bc9`. Head = `d6e15f5d...2a7c`, MBR 55AA, disk-id 0x85d82b93, a single type-83 entry, sectors 1-15 zero, U-Boot embedded byte-exact at 8192 with zeros after it, eGON checksum valid. Main U-Boot contains `bl31.bin` and is **not** the recovery build.
7. **Boot chain in the image:** `armbianEnv.txt` has `rootdev=UUID=e70cdb2c-...`, `fdtdir=/boot/dq10-dtb`, `fdtfile=sun50i-h616-dq10-athena-p1.dtb`. Armbian `boot.cmd` honours `fdtdir`, and the file exists there and in `dtb-6.18.53.../allwinner/`. `fstab` uses the same UUID. ext4 features are identical to Armbian's original (`metadata_csum_seed` is read-OK in U-Boot: `INCOMPAT_SUPP_LAZY_RO`). U-Boot uses the DOS label (`part_test_efi` requires a protective MBR), so the vendor backup GPT is ignored. Boot-critical drivers are built in (`MMC_SUNXI`, `MFD_AXP20X_I2C`, `REGULATOR_AXP20X`, `I2C_MV64XXX`, `PINCTRL_SUN50I_H616(_R)`, `PWRSEQ_SIMPLE`, `DRM_SUN4I`/`SUN8I_*`, `EXT4`). U-Boot `mmc 1` = eMMC (`aliases`), so the recovery `ums 0 mmc 1` is consistent.
8. **Wipe ranges:** p1 bounds are computed from sysfs at run time; it zeroes only [8192, p1_start) and [p1_end, end). It is ordered `Before=armbian-resize-filesystem` and the resize has `Requires/After` the wipe. A re-run after resize is still safe, because it uses the new bounds. It refuses unless root = `<disk>p1`, there is a single partition, an eMMC boot partition exists, and eGON is present at sector 16. The resize script was checked (`/usr/lib/armbian/armbian-resize-filesystem`, no growroot in the initramfs).
9. **Wi-Fi wiring:** PG10 `x32clk_fanout_pin` (`function = "clock"`) and `CLK_OSC32K_FANOUT` exist in 6.18.53 `sun50i-h616.dtsi`; PG18 active-low pwrseq is correct for WL_REG_ON. Firmware path `/lib/firmware/aic8800_fw/SDIO` + `/aic8800D80` is compiled into `aic8800_bsp`, and all U02 files are installed. `wpasupplicant`, `iw`, `netplan.io`, networkd (in `systemd`), `mmc-utils` and `python3` are installed.
10. **Stick tooling:** toybox 0.8.4 `dd` supports `conv=notrunc,fsync`, `skip/seek/count`; `blockdev --flushbufs/--getsize64`, `zcat`, `pidof`, `sha256sum`, `nohup` (toybox) all exist. SELinux is Permissive and the kernel is 5.4.125 (no write-to-mounted-bdev restriction). Writes through `/dev/block/mmcblk0` use a page cache separate from the dm/partition devices; the regions do not overlap. `sync` + `BLKFLSBUF` + `drop_caches` before the read-back makes it read the media. O_DIRECT is not available in this toybox (`iflag` only `count_bytes`/`skip_bytes`). The scripts are LF-only.

## Could not verify

- EXT_CSD (BOOT_PARTITION_ENABLE / BOOT_BUS / BOOT_ACK): no debugfs on the stick and no `mmc` binary; mounting debugfs is outside the read-only rules. Not needed, for the reason in verified item 4.
- Whether the BROM falls back to sector 512 on a bad sector 16 on this exact chip (only the U-Boot source comment and the vendor's dual copy suggest it).
- FEL reachability (USB never enumerated); the recovery U-Boot behaviour.
- The meaning of TPR13 bits 5/6/13/14 in the BSP, and whether LPDDR3 @600 MHz on the mainline driver trains on this board.
- HDMI pipeline (Armbian DT patches + `hvcc-supply = aldo1`); SD-slot voltage wiring; LED colours.
- Struct-layout equality for the AIC modules beyond `struct module` (M3).
- AIC firmware redistribution licence (Radxa ships it; the terms were not found).
- The PMIC chip-ID byte on this unit (the vendor says AXP1530; 0x48 expected).
