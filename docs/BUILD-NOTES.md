## 2. Which SoC is it?

* Vendor props: `ro.soc.model=H618`, DT compatible `allwinner,h616`, `ro.boot.hardware=sun50iw9p1`, `sunxi_chiptype 0x00002100`, `sunxi_secure normal`, 4x Cortex-A53, cpufreq max 1512 MHz.
* eFuse/SID word 0 (nvmem `sunxi-sid0`, first 4 bytes only; the rest of the SID is a per-chip identifier and was deliberately not recorded) = **`0x33802100`**. Reference table (Kaiser gist): H313 `32c05c00`, H616 `32c05000`, **H618 `33802000`**, H700 `33806c00`. The prefix `3380 2` matches H618; bit 8 differs (same kind of variation as H3 `...81` vs `...181`). **Conclusion: most likely an H618 (confidence M-H), not H313/H616.** All three share one mainline target (`MACH_SUN50I_H616`, TF-A `sun50i_h616`, same DRAM driver) so nothing in the build depends on this; the DT keeps `allwinner,sun50i-h616` as in the TX1.
* Consequence: the CPU speed-grade cell (low 16 bits of word 0 = `0x2100`) is **not in the mainline `sun50i-cpufreq-nvmem` table** (known: 0x2000, 0x2400, 0x7400, 0x2c00, 0x7c00, 0x5000, 0x5400, 0x6000, 0x5c00, 0x5d00, 0x6c00). Mainline will log "unknown speed bin 0x2100, using default bin 0" and use the most conservative OPPs - safe, possibly slower than the vendor's 1.5 GHz. SPL itself runs the CPU at 1008 MHz.

## 3. DRAM parameters (the highest-risk item) - decoded and cross-checked

### 3.1 Sources and agreement
* vendor DT `dram` node (live-fdt.dtb): 32 cells `dram_para[00..31]`.
* vendor **boot0** found in the backup at byte 0x2000 (sector 16) and again at 0x40000 (sector 512): `eGON.BT0`, length 61440, checksum `0x29b807b1` (**I re-computed the BROM checksum with stamp 0x5F0A6C39 and it matches**, so my understanding of the checksum rule is right), both copies byte-identical. sha256 of that 61440-byte image: `2adbfcbc4da37a8abdc8570675fd13a18f6ddf0de686f2dfa9594d4572bbcda3`.
* The 32 words at boot0 offset 0x38 are **identical to the DT cells (32/32)**: no disagreement.
* boot0 also carries an extended-parameter block (`DRAM.ext`, magic at word 210): all 15 alternative parameter sets are **empty**, so this boot0 has exactly one DRAM profile (no runtime selection between chip vendors).
* vendor boot0 strings confirm: LPDDR3 `DRAM Type =%d (3:DDR3,4:DDR4,7:LPDDR3,8:LPDDR4)`, `PMU: AXP1530`, `chip id check OK`, `DRAM_VCC set to %d mv`, `NO support for more than 2048M`, and `eraly jump fel` / `carshdump mode , jump fel` (FEL is reachable from the vendor boot0 via an RTC flag).

### 3.3 What can still go wrong
1. Mainline's LPDDR3 timing sets (hard-coded) might not match this board's exact LPDDR3 chips. **Status after the FEL test: DRAM init passes and 2 GiB read back correctly with 9 random patterns plus the alias test (sec. 5). Remaining: long-duration stability (run the pattern test longer and memtester under Linux) and the effect of heat.**
2. TPR1 (0x80000000) and TPR13 (0x6061) are dropped (not in the mainline driver).
3. The mainline driver may differ in training behaviour (it does read calibration only; vendor enables the same set).

## 4. PMIC and voltages (explicit, because a wrong DRAM voltage can break boot)

* Vendor name **AXP1530**, I2C addr **0x36** on **R_I2C** (`twi@7081400`, "i2c5"). Mainline name **AXP313A** (the Linux patch series began as "AXP1530" and was renamed because every part seen is marked AXP313a). TF-A v2.15.0 `sunxi_power.c` explicitly treats **reg 0x03 value 0x48 = "AXP1530"** (also 0x4b AXP313A, 0x4c AXP313B) as AXP313; U-Boot `axp_spl.c` accepts `(reg03 & 0xc8) == 0x48`. The vendor boot0 prints "PMU: AXP1530" / "chip id check OK". **Support: U-Boot `CONFIG_AXP313_POWER` (SPL, I2C 0x36), TF-A (needs `x-powers,axp313a` in the DT it is given - the TX1 DT used by U-Boot has it), Linux `x-powers,axp313a` (MFD axp20x + regulator) - all mainline. Confidence H that the code paths exist; M that the chip on the board answers as 0x48 (not read directly).**
* Live regulator state (`/sys/class/regulator`, read-only) and vendor DT:

| regulator | live | vendor DT range | role (evidence) | mainline setting |
|---|---|---|---|---|
| dcdc1 | 0.96 V | 0.5-3.4 V | `hdmi_power1`, GPU/SYS ("vdd-gpu-sys") | `reg_dcdc1` 0.81-0.99 V always-on (as TX1); **U-Boot cannot set DCDC1 for AXP313** (no Kconfig), left at OTP default |
| dcdc2 | 1.10 V | 0.5-1.54 V | `cpu-supply` | `reg_dcdc2` 0.81-1.12 V; SPL sets `AXP_DCDC2_VOLT=1000` (Kconfig default) before raising the CPU to 1008 MHz (vendor OPP for 1008 MHz: 0.94-1.02 V depending on bin) |
| **dcdc3** | **1.20 V** | 0.5-1.84 V | **DRAM** (standby `vcc-dram`; boot0 "DRAM_VCC") | **`CONFIG_AXP_DCDC3_VOLT=1200`** (Kconfig default is 1100 = LPDDR4 value and would under-volt LPDDR3 VDD2) - same as TX1; DT fixes it at exactly 1.2 V |
| aldo1 | 1.80 V | 0.5-3.5 V | `vqmmc` (eMMC, SDIO), `hdmi_power0`, PLL | `reg_aldo1` 1.8 V always-on |

* Unknown: the PMIC power-on defaults of this unit (dcdc3 before software touches it). The vendor boot0 sets 1.2 V itself, as does our SPL, before DRAM init (order verified in `sunxi_board_init`).

## 5. Boot ROM / eMMC boot behaviour (answers to the specific questions)

* **Vendor layout (from the backup):** GPT at LBA 1 with 25 entries (sunxi), 128 entries' worth never used. boot0 (eGON.BT0, 61440 B) at **sector 16 (8 KiB)** and a second identical copy at **sector 512 (256 KiB)**; `boot_package` ("sunxi-package", holds u-boot 2018.07, monitor/optee, DTB) at sector 24576 (12 MiB) and 32800; second GPT-looking structure at 0x1400200. First partition (`bootloader_a`) starts at sector 73728.
* **Where the H616 BROM looks (from U-Boot v2026.10 source, `arch/arm/mach-sunxi/board.c` and `doc/board/allwinner/sunxi.rst`):** SD/eMMC: eGON SPL at **sector 16 (8 KiB)** first; "newer SoCs" then a second location, which for **H616 is 256 KiB (sector 512)** - not 128 KiB as the generic doc text says (the code comment: "The H616 has the alternative location moved up to 256 KB instead of 128KB"; mainline `board_spl_mmc_get_uboot_raw_sector` adds `(128-8)*2 + 128*2` sectors for the high location on H616). That is exactly where the vendor keeps its second copy. Our single image at sector 16 therefore is the primary location. The BROM also supports **eMMC hardware boot partitions** (needs BOOT_ACK and a boot-bus config in EXT_CSD; SPL expected at offset 0 of boot partition 1/2); it checks the SPL checksum itself. SPI flash has lowest priority; SD (SMHC0) is tried before eMMC; if no valid image is found anywhere the BROM enters **FEL** (USB).
* **Hardware boot partitions of this eMMC (read-only check):** `mmcblk0boot0/1` exist, 8192 sectors (4 MiB) each, `force_ro=1`, and **both read as all zeros** (sha256 of each = the SHA-256 of 4 MiB of zeros, `bb9f8df6...3af8`). So nothing lives there and, since the stick boots from the user area, the BOOT_PARTITION_ENABLE field is evidently not selecting them (EXT_CSD itself could not be read: no debugfs/mmc-utils on the stick; unverified).
* **What happens when our SPL is...**
  * *checksum-invalid or magic missing at sector 16*: BROM rejects that location, tries sector 512, then the other media (SD card first/last depending on order, SPI), then **FEL**. With the whole eMMC wiped (our plan) this ends in FEL - recoverable *if* FEL works.
  * *valid but fails later* (DRAM init hang, U-Boot FIT unreadable): the BROM has already jumped into SRAM; **there is no fallback** - the device hangs (mainline SPL does not return to the BROM on this path; unverified) and FEL is not entered automatically. Only a hardware trick (see FLASH-PLAN 7: short the eMMC clock, or an SD card with the sunxi-tools `fel-sdboot` image, which the BROM tries *before* the eMMC) gets out.
  * *a fallback copy*: placing a second full image at sector 512 is impossible - our U-Boot image (790 KB) at 8 KiB spans sectors 16-1559 and would overlap it; and a second copy would be byte-identical anyway. So there is one copy, written last and atomically committed (sector 16 last).
* **FEL: PROVEN (2026-10-29, by the main session, zero eMMC writes).** `reboot efex` from the vendor Android put the stick into FEL; the laptop saw USB `1f3a:efe8`; attached to WSL with usbipd-win (`usbipd attach --wsl --hardware-id 1f3a:efe8`), `sunxi-fel ver` -> H616 family (soc 0x1823), SID word 0 `33802100`; `sunxi-fel -v spl uboot/u-boot-sunxi-with-spl.bin` (pre-fix build sha256 `2c792ef3...0909`) ran **our SPL, DRAM init succeeded and returned to FEL**; sunxi-fel then loaded TF-A to 0x40000000 and U-Boot to 0x4a000000; 2 MiB random-pattern write/read-back OK at 0x42000000, 0x50000000 ... 0xB0000000, 0xBFE00000 (9/9); alias test at 0x40001000/0x60001000/0x80001000/0xA0001000 intact -> **full 2 GiB, no aliasing**. (This reverses my earlier "FEL plausibility LOW", which was based on the owner's observation that the laptop never saw the stick while Android was running: Android uses USB0 as host, BROM FEL uses it as device.)

## 6. U-Boot / TF-A build decisions

* Config `uboot/dq10_athena_p1_defconfig` = `tanix_tx1_defconfig` (v2026.10) with: DRAM block replaced by sec. 3, `DRAM_CLK=600`, `AXP313_POWER` + `AXP_DCDC3_VOLT=1200` (kept), SPL status LED = **GPIO 230 (PH6)** (vendor `gpio_para`: normal_led = PH6; TX1's own value 231 contradicts its DTS, so I used the vendor value). **Revision 4: PH6 is ACTIVE-LOW (hardware, 2026-10-30), so `# CONFIG_SPL_SUNXI_LED_STATUS_ACTIVE_HIGH is not set`** (U-Boot `board/sunxi/board.c status_led_init()` drives the pin to that state at SPL start = lit). **Revision 4 also sets `CONFIG_AUTOBOOT_KEYED=y`, `CONFIG_AUTOBOOT_STOP_STR="dq10stop"`** (BOOTDELAY=2 stays; only that string on the console can stop autoboot, line noise cannot), `MMC_SUNXI_SLOT_EXTRA=2` and `SUPPORT_EMMC_BOOT=y` (eMMC on SMHC2 = U-Boot "mmc 1", and mmc 0 when it is the boot device), USB EHCI/OHCI as TX1.
* U-Boot device tree (revision 2): **`allwinner/sun50i-h313-dq10`** = a local file (`uboot/sun50i-h313-dq10.dts`, placed in `dts/upstream/src/arm64/allwinner/` of the build tree, not upstream) that includes the Tanix TX1 DT (same PMIC/eMMC/UART0/USB wiring; TF-A reads `x-powers,axp313a` from it) and enables the SD slot on SMHC0 (`vmmc = dldo1`, 4 bit, `broken-cd`, `disable-wp`). Revision 1 reused the TX1 DT unchanged, whose SD node is disabled; the auditor showed that this made an SD card invisible to U-Boot proper (H2). U-Boot proper needs no HDMI. `fdtfile` is overridden by `armbianEnv.txt`.

## 9. Image and vendor-blob audit

* Base: Armbian tx6s-axp313 (H616 + AXP313, mainline-based kernel 6.18.53, same architecture of power/eMMC as ours) because it is the only current official Armbian build for a TV box with this PMIC; the kernel/rootfs are board-agnostic; the board-specific parts are U-Boot (replaced by ours) and `armbianEnv.txt`/DTB (replaced).
* **SSH (revision 2; since publication the key is optional):** `scripts/build-image.sh` installs a *public* key given as `AUTHORIZED_KEY=path` as `/root/.ssh/authorized_keys` (the private key is never read or copied; without `AUTHORIZED_KEY` nothing is installed) (dir 0700, file 0600, root:root) and `/etc/ssh/sshd_config.d/00-dq10.conf` sets `PermitRootLogin prohibit-password`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no` (sshd keeps the first value; `Include` is at the top of `sshd_config`). Armbian's `armbian-firstrun` only regenerates host keys / edits `AcceptEnv`; `armbian-firstlogin` writes `authorized_keys` only for `PRESET_ROOT_KEY` (unset), so nothing undoes it. Nothing waits for a console password during boot: the console shows a login prompt and, after login, "Press Enter to start the first login setup" (wizard: new root password, shell, user, locale). Default console password `1234` works on the console only.
* Modifications (script `scripts/build-image.sh`, reproducible): partition 1 extracted, our DTB added at `/boot/dq10-dtb/` (survives dtb-package updates) and into the kernel dtb dir, `armbianEnv.txt` gets `fdtdir=/boot/dq10-dtb`, `fdtfile=sun50i-h616-dq10-athena-p1.dtb`; `/lib/firmware` pruned from 445 MB to the regulatory database + the AIC8800D80 set; `armbian-firmware*` marked `hold` in dpkg; hostname `dq10`; first-boot wipe service; Wi-Fi modules; filesystem shrunk then grown to exactly 1.25 GiB (327680 4K-blocks), UUID `e70cdb2c-6e3a-442f-9d56-99fd4c5ecae5` unchanged.
* Remaining third-party binary blobs in the rootfs: only the AIC8800D80 firmware (Radxa package) - needed for Wi-Fi; `wireless-regdb` data. No Android, no vendor boot0/u-boot, nothing from the stick. The Linux kernel itself and the Debian userland are standard distribution binaries (Armbian-built); the SPL/BL31 are built from source here.
* **Not covered:** the eMMC controller firmware, the SoC BROM and eFuses are not replaceable (see the BROM post-flash check in FLASH-PLAN 8). Wi-Fi chip flash/ROM is not touched.
* Threat note: the vendor Android on the stick is compromised (see `MALWARE-IOCS.md`). Consequence for the flash: do not trust on-device `sha256sum` output as the *only* verification (a hostile root userland could lie); the independent proof is the post-flash boot into code we built, followed by the BROM/eMMC checks from that code. Keep the stick on the isolated network, and re-apply the iptables egress block after any reboot before the flash.

## 10. Disk layout used for flashing (why it is not the stock "partition at 4 MiB" layout)

The ready-made `dq10-armbian.img` (partition at sector 8192) would have to overwrite the vendor `super` partition that the running Android uses as its read-only system. `lpdump` (read-only) shows `super` (disk sectors 599040-6890495) holds system/vendor/product/vendor_dlkm as linear dm mappings on `179:9` up to super-sector 3,422,520, i.e. **disk sector 4,021,560**; the remaining **1.37 GiB of super is unused** and nothing writes it (ext4 mounted `ro`, no dm-verity device present, no OTA running). The rootfs is therefore staged at **disk sector 4,194,304 (2 GiB)**, size 2,621,440 sectors (1.25 GiB) -> ends at 6,815,744 < 6,890,496; the front 4 MiB (MBR + SPL + U-Boot) is written last. Android keeps running (and bootable) until the final sub-second commit. After first boot the wipe service zeroes everything else and Armbian grows partition 1 to the end of the disk.

**PHY0 routing (read in the 6.18.53 tree):** `phy-sun4i-usb.c` takes `data->dr_mode = of_usb_get_dr_mode_by_phy(np, 0)` = the `dr_mode` of the FIRST enabled DT node whose `phys` references PHY0 - `usbotg` precedes `ehci0` in `sun50i-h616.dtsi`. **VBUS:** with no `usb0_vbus_det` GPIO and no `usb0_vbus_power-supply` the driver reports VBUS valid (forced `FORCE_VBUS_VALID`, `sun4i_usb_phy0_get_vbus_det()` fallback 1), so the A-A cable's VBUS is irrelevant for the gadget. The `usb0-vbus` regulator-fixed node stays; with no consumer the core leaves PH8 as requested output low.
**Possible shared cause with the U-Boot UMS failure:** unknown, so not excluded. * Identity check vs "Windows wrote bootloader_a": if the compare shows `preboot-area` differs, the dry run refuses and `--skip-identity` is needed; only do that after understanding why.
